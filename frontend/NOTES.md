## Решения о подаче данных

- Все семь экранов используют один выбранный расчёт. Длительные операции имеют статус и блокировку повторных команд; при смене расчёта данные и открытые карточки предыдущего расчёта сбрасываются.
- Оператор задаёт цель и сообщения. Ручного назначения задач аппаратам и редактирования текущего внутреннего состояния нет.
- Карта затрат разделяет энергию **сверх ожидания** и **полную нагрузку без солнца/нагревателя**. Температурная величина подписана как сдвиг равновесия, не фактический нагрев. Это не денежная себестоимость.
- «Нет наземного контакта» и «Нет доступных сеансов обоих типов» показаны отдельно. Наличие бандла само по себе не означает возможность выполнения job. Защита шлюза — логика расширения планировщика, не доказательство физического поддержания связи.
- `/flow` не имеет offset. Если корзина обрезана, полный поток восстанавливается из согласованного экспорта: исходные задания, add_jobs и успешные действия trace. Проверяются полнота и согласованность со сводкой; усечённые данные не выдаются за полный список.
- Trace загружается непересекающимися окнами шагов в пределах лимита API. На P04 это 0–95,96–191,192–287.
- Файл событий разбирается на отдельные сообщения. Будущие события отправляются **на своей границе**, перед выполнением следующего шага. Очередь хранится в sessionStorage этой вкладки. При ошибке перечитываются состояние и лента; подтверждённые сервером события убираются из очереди. Частично принятый файл не называется полностью отклонённым.
- `events_demo.json` помечен P02, хотя сценарий приёмки ТЗ предлагает его для P04. UI явно предупреждает о несовпадении и называет текущий сценарий на кнопке отправки. Сервер проверяет содержимое в контексте выбранного расчёта.
- Контрольная точка сохраняется **до** продолжения отдельной веткой. Произвольной перемотки назад в API нет. Неизменность источника и одинаковость продолжений проверяются.
- При создании ветвей передаётся полный config исходника, иначе backend сбрасывает параметры к defaults. Вердикт показывается дословно с сервера, по цели A; UI не вычисляет свой «победитель».
- JSON сохраняется и отправляется как исходный текст, без повторной сериализации чисел JavaScript. HTML экранирует пользовательские строки и предназначен для чтения/печати.
- HashRouter обеспечивает открытие и обновление внутренних страниц при раздаче `dist` имеющимся сервером без настройки SPA fallback.

## Чего не хватает в API и что осталось ограниченным

1. **Полный каталог заданий/аппаратов до запуска.** `GET /scenarios/{id}` отдаёт сводку, preflight — максимум 200 невыполнимых заданий. Поэтому до запуска карта любого задания открывается по ID; заряд/приоритет меняются вводом существующего ID. Выпадающий полный каталог всех заданий до запуска не реализован. Нужен read-only маршрут исходного сценария или каталог с пагинацией.
2. **Карта стоимости задания, пришедшего add_jobs.** Существующий маршрут ищет только в исходном сценарии и возвращает 404. UI объясняет ограничение. Нужен маршрут стоимости в контексте run.
3. **Мгновенный полный explain старого шага.** Сервер хранит полный разбор только последних 24 шагов, более ранний пересчитывает. Предел 300 мс на содержание нельзя обещать. У baseline/federated также может не быть net_value/теневых цен; отсутствующие поля не заменяются выдуманными числами.
4. **Пары step/satellite_id для причин ожидания.** Analytics возвращает агрегат, trace — причину модели. Точный переход по причине планировщика ищет совпадения через explain порциями 96. Это может быть медленно для старой истории; нужен фильтруемый журнал причин планировщика.
5. **Контрольные точки/очереди не являются долговременным серверным хранилищем.** Прогоны живут в памяти API. Перезапуск сервера теряет расчёты и точки. Очередь будущих сообщений принадлежит вкладке; export содержит только уже принятые события. Продолжение через другой клиент не применит браузерную очередь.
6. **Импорт — проверка, а не регистрация запуска.** API повторяет команды и события, сравнивает переданные поля summary. Отдельно trace и initial_scenario_hash не сверяет, продолжить импортированный расчёт на пульте нельзя. UI не заявляет такую возможность.
7. **Сравнение не транзакционно между HTTP-запросами.** UI проверяет происхождение и горизонт, но другой клиент может вмешаться в процесс. При сетевом обрыве уже созданные ветви остаются в списке. При одинаковом mode backend копирует planner независимо от имени; смена алгоритма внутри сравнения не предлагается.

Манёвры уклонения, LLM, самообучение и кэширование наземной передачи не входят в реализацию: соответствующих операций и данных в текущем ТЗ/API нет. Здесь отображается фактическая модель ресурсо- и задачепланирования.

## Как запустить и передать

Передать Сергею **только папку frontend** из архива, заменив ею одноимённую папку его репозитория. Backend/model/data и корневые Docker-файлы брать из его репозитория.

```powershell
# В папке frontend
npm ci
npm run dev
npm run build
```

По умолчанию Vite:5017 → API:8000. Если сервер запущен на 5018:

```powershell
$env:COSMO_API_TARGET = 'http://127.0.0.1:5018'
npm run dev
```

Корневой `docker compose up -d` продолжает использовать переданную конфигурацию команды. Новых библиотек frontend не добавлено. Архив включает готовый `dist`, исходники, lockfile, этот отчёт, превью и воспроизводимые проверки. `node_modules`, `.qa`, временные результаты и локальные Python-зависимости исключены.

## Короткий сценарий демонстрации

1. Предполётная оценка → P04_demand. Проверьте 112,1% relay и 34 аппарата с дефицитом. Нажмите ID структурно невыполнимого задания для карты затрат.
2. При необходимости раскройте изменение сценария; например, S01 →75%, JOB-0007 →P3. Сохранится отдельный вариант.
3. Пульт → выберите сценарий/цель/режим → «Начать смену». В потоке заданий работают фильтры и сортировки.
4. На пульте выполните до 72 и **сохраните точку**. Загрузите examples/events_demo.json, подайте JSON. Событие 72 будет принято, более поздние попадут в очередь.
5. Продолжите смену; цель можно менять на границе. Пауза останавливает после текущего запроса, пакет не превышает 12 шагов. Принятые события и смены цели видны справа.
6. Группировка → ячейка матрицы или форма под ней → разбор. Аналитика → KPI/причина → соответствующие операции.
7. Сравнение → точка 72 → «Цена автономии» → конечная граница → рассчитать. Посмотрите серверный вердикт, дельты и отличия заданий.
8. Выгрузка → сохранить JSON. Загрузите его обратно → «Проверить воспроизведение». Для читаемой версии подготовьте отчёт и скачайте HTML или распечатайте.
