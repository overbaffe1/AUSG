## 3. Задачи по приоритету

Приоритет определён критериями оценки: О5 «Работа оператора» (7 баллов) требует, чтобы эксперт **самостоятельно** прошёл основной сценарий, О3 «Обоснованность» (8 баллов) — чтобы он разобрал конкретное решение.

### И1. Разбор решения — КРИТИЧНО (критерий О3)

Самый ценный экран: он показывает, что система не чёрный ящик.

**Данные:** `GET /api/runs/{id}/explain?step=&satellite_id=` возвращает:
- `requested`, `executed`, `reason_code`, `reason_text`;
- `considered.top_candidates` — рассмотренные задания с `net_value`;
- `considered.shadow_prices` — цены ресурсов в этот момент (`ground_slot`, `energy_wh`, `sat_step`);
- `considered.rejected` — отклонённые с причинами;
- `consequences` — энергия и температура до и после, нагрузка, нагреватель, возраст калибровки, завершённое задание, флаги `below_reserve` и `brownout`;
- `mismatch` — расходится ли запрошенное с исполненным;
- `detail_available` — есть ли уже глубокая часть (`rejected`, `detail`).

**Два уровня ответа.** По умолчанию ручка отвечает **за 8–30 мс на любом
шаге**: действие, причина, теневые цены и `top_candidates` хранятся всегда.
Глубокая часть — список отклонённых и карта стоимости — у старых шагов не
хранится ради памяти и восстанавливается повтором прогона: `?full=true`,
до пяти секунд на `P04_demand`, повторный запрос того же шага мгновенный.

Поэтому панель открывается сразу на быстром ответе, а если
`detail_available = false` — показывает кнопку вроде «разобрать
подробно», которая дозапрашивает `full=true` со статусом ожидания.
Вызывать `full=true` при каждом открытии панели нельзя: критерий приёмки
ниже этого не переживёт.

**Что сделать.** Боковая панель, открывается кликом по ячейке расписания или строке аппарата. Показать: что выбрано и почему, какие были альтернативы с их чистой ценностью, какие цены ресурсов действовали, что именно заблокировало отклонённых, каковы последствия по энергии и температуре.

**Обязательно:** причины простоя, отказа в операции и срыва задания — **разные вещи**, не смешивать в одну строку. Если `mismatch = true`, это видно явно.

**Приёмка.** Панель открывается быстрее 300 мс на `P04_demand`, видны `net_value` и теневые цены.

### И2. Поток заданий (критерий О1, О5)

Главный экран продукта: система управляет **потоком заданий**, здесь он и виден.

**Данные:** `GET /api/runs/{id}/flow` — четыре корзины `completed` / `in_progress` / `waiting` / `missed`, у каждого задания `kind`, `priority`, `value_usd`, окно, `remaining_steps`, `progress`, `eligible_satellites`. Плюс `GET /api/scenarios/{id}/jobs/{job_id}/cost` — карта стоимости по каждому исполнителю.

**Что сделать.** Виртуализированная таблица (на `P04_demand` до **8120 строк** — без виртуализации будет тормозить). Фильтры по статусу, типу, приоритету, исполнителю. Сортировка. Клик по заданию открывает карту стоимости: сколько ватт-часов, слотов наземного сегмента, шагов аппарата и градусов оно стоит.

**Приёмка.** 8120 строк, скролл без рывков, фильтры мгновенные.

---

### И3. Ввод сообщений и смена цели (критерий О2, О5)

Единственный способ вмешательства оператора. Без него основной сценарий жюри не проходится.

**Данные:**
- `POST /api/runs/{id}/events` — принимает **один объект события без обёртки** (так подаёт жюри) либо файл `cosmo-B-events-1.0` целиком;
- `POST /api/runs/{id}/events/manual` — `{type, satellite_ids, end_step}`, `at_step` подставляет сервер;
- `POST /api/runs/{id}/objective` — смена цели на границе шага.

**Что сделать.**
1. Загрузка JSON файлом и вставкой текста.
2. Ручной ввод: выбор типа (`satellite_outage` / `close_downlink`), мультиселект аппаратов, конец интервала.
3. Понятное сообщение при отклонении: повторный `id`, чужой шаг, битая структура. **Состояние при этом сохраняется** — показать это пользователю явно.
4. Переключатель цели с историей смен.
5. Лента принятых сообщений.

**Приёмка.** Повторная подача того же события даёт внятную ошибку, расчёт продолжает работать.

### И4. Сравнение вариантов (критерий О4, 7 баллов)

**Данные:** `POST /api/runs/{id}/branch` (`{objective, mode, planner, label}`), `GET /api/compare?a=&b=` — возвращает `deltas`, `comparable_state` и готовый `verdict` с текстом.

**Что сделать.** Выбор контрольного шага, создание двух ветвей с разными настройками, side-by-side: таблица дельт, парные графики, подсветка заданий, различающихся по статусу. Блок вердикта — **текст берётся с бэкенда, UI не выдумывает выводы**.

Отдельный сюжет: сравнение `centralized` против `federated` показывает **цену автономии в деньгах**. Вынести это как готовый пресет — одна кнопка.

**Приёмка.** Две ветви создаются в три клика, различия видны без поиска глазами.

### И5. Группировка и связь (критерий О5)

**Данные:** `GET /api/runs/{id}` — по каждому аппарату `soc_pct`, `temp_c`, `calibration_age_steps`, `calibration_valid_for`, `available`, `in_contact`. `GET /api/runs/{id}/trace` — журнал с фильтрами. `GET /api/runs/{id}/bundles` — полётные задания в федеративном режиме.

**Что сделать.**
1. Карточки аппаратов; графики SOC(t) и T(t) с отмеченными границами: резерв 30%, критический 20%, рабочий диапазон −5…+45 °C.
2. **Таймлайн-матрица «аппараты × шаги»** с цветовой кодировкой действия. На `P04_demand` это 48 × 288 = 13 824 ячейки — рисовать через canvas или виртуализацию, не DOM-элементами.
3. **Индикатор связи с Землёй:** кто сейчас шлюз, сколько аппаратов в контакте. Подсветить шаги полной слепоты — в `P02/P03/P04` это шаги **224 и 230**, в `P01_intro` оба канала недоступны 85% смены с разрывом до 37 шагов подряд (шаги 11–47). На таких шагах задания выполнять нельзя по модели — подписывать их как «нет доступных сеансов», а не «автономная работа».
4. Бандлы: что загружено на борт, когда и до какого шага действует. Должно быть видно, что аппарат вне связи работает по старому полётному заданию.

**Приёмка.** Матрица рендерится плавно, клик по ячейке открывает панель И1.

### И6. Аналитика (критерий О1)

**Данные:** `GET /api/runs/{id}/analytics` — `summary`, `priority_service`, `utilisation`, `blocked_reasons`, `idle_reasons`, `ground_link`, `lost_work`, `energy`.

**Что сделать.** KPI-плитки, диаграмма причин отказов, тепловая карта загрузки аппаратов, график использования лимита наземного сегмента. Числа кликабельны — переход в отфильтрованный журнал.

**Правила учёта, нарушение которых стоит баллов** (описание данных, с. 10–11):
- доля выполнения приоритетных заданий при **нулевом знаменателе отсутствует** — показывать прочерк, не «0%». Бэкенд отдаёт `null`, не превращай его в ноль;
- загрузка аппарата — доля шагов **заданий**; ожидание и калибровка показываются отдельно;
- невыполненные задания не исчезают из знаменателя.

### И7. Настройка сценария и выгрузка

**Данные:** `POST /api/scenarios/upload`, `POST /api/scenarios/{id}/derive`, `GET /api/runs/{id}/export?include_trace=`, `POST /api/runs/import`.

**Что сделать.**
1. Загрузка своего сценария файлом с показом ошибок валидации.
2. Форма модификации: начальный заряд выбранного аппарата, коэффициент солнечной мощности, приоритет существующего задания. Сохраняется как новый сценарий. Клиент `derive` уже есть, UI нет.
3. Кнопки «Сохранить расчёт» (JSON) и «Отчёт» (читаемый HTML или печать).
4. Экран импорта: загрузить выгрузку и показать подтверждение «Расчёт воспроизведён, показатели совпали».

**Важно:** на `P04_demand` выгрузка с `trace` весит десятки мегабайт. Дать переключатель `include_trace`.

## 4. Общие требования к интерфейсу

- **Система работает сама.** Оператор не назначает исполнителей вручную и не редактирует внутреннее состояние — постановка это прямо запрещает. Никаких кнопок «назначить задание аппарату».
- **Длительная операция сопровождается статусом**, ошибка — понятным сообщением. Кнопки блокируются на время запроса.
- **Данные разных прогонов не смешиваются.** Переключение между расчётами полностью меняет контекст.
- **Ошибки бэкенда** приходят как `{"error": {"code", "message", "details"}}` — показывать `message`, `details` разворачивать по требованию.
- Работоспособность важнее украшений. Количество технологий и сложность интерфейса преимуществом не являются.

## 5. Как работать

```bash
docker compose up -d              # интерфейс на 5017, API на 5018
docker compose logs -f web
```

Код проброшен томом, правки подхватываются **без пересборки**: бэкенд перезапускается сам, фронтенд обновляется в браузере.

- Интерфейс: `http://localhost:5017`
- API напрямую и интерактивная документация: `http://localhost:5018/docs`
- Запросы из интерфейса идут на `/api/...` — Vite проксирует их на бэкенд, CORS не мешает.

Локально без Docker:

```bash
uvicorn backend.app.main:app --reload          # 8000
cd frontend && npm install && npm run dev      # 5017, проксирует на 8000
```

**Перед завершением каждой задачи:**

```bash
cd frontend && npm run build    # tsc strict должен пройти без ошибок
```

Проверять на `P04_demand` — 48 аппаратов, 288 шагов, 8120 заданий. То, что летает на `P01_intro`, может лечь на боевом объёме.

## 6. Сценарий, который должен проходиться целиком

Это и есть приёмка по критерию О5. Посторонний человек без подсказок должен суметь:

1. Открыть `http://localhost:5017`.
2. Выбрать `P04_demand` и увидеть **до запуска**: переподписка 112% по ёмкости с учётом окон связи, 34 аппарата в энергодефиците, список структурно невыполнимых заданий, потолок выручки.
3. Открыть любое задание и увидеть его карту стоимости.
4. Изменить начальный заряд аппарата и приоритет задания, сохранить как новый сценарий.
5. Выбрать цель и режим, запустить, наблюдать поток заданий.
6. Остановиться на шаге 72, подать `examples/events_demo.json`, продолжить.
7. Кликнуть любое решение и получить разбор.
8. Вернуться к контрольному шагу, создать две ветви, сравнить, прочитать вердикт.
9. Увидеть цену автономии — разницу между централизованным и федеративным режимом.
10. Скачать выгрузку и загрузить обратно с подтверждением воспроизведения.
