## Слайд А. «Четыре слоя и одна граница»

**Подзаголовок:** Модель кейса не переписана ни на строку — всё построено поверх неё.

```
┌──────────────────────────────────────────────────────────────┐
│  КОНСОЛЬ ОПЕРАТОРА          React 18 · TypeScript strict      │
│  7 экранов, 1 435 строк     Vite 6 · Recharts · Zustand       │
│  предполётная оценка · пульт смены · поток заданий ·          │
│  группировка · разбор решения · сравнение · аналитика         │
└───────────────────────────┬──────────────────────────────────┘
                            │  HTTP/JSON, 24 ручки
                            │  единый формат ошибки
                            ▼
┌──────────────────────────────────────────────────────────────┐
│  ВЕБ-СЛОЙ                   FastAPI · pydantic v2 · uvicorn   │
│  тонкий: только валидация, изоляция прогонов, сериализация    │
└───────────────────────────┬──────────────────────────────────┘
                            ▼
┌──────────────────────────────────────────────────────────────┐
│  ЯДРО ПОТОКА ЗАДАНИЙ        4 096 строк Python, без ML        │
│  оценка → себестоимость → теневые цены → допуск →             │
│  диспетчеризация → объяснение                                 │
│                                                               │
│  ДВА РЕЖИМА ИСПОЛНЕНИЯ                                        │
│  centralized: ЦУП решает за всех на каждом шаге               │
│  federated:   ЦУП шлёт полётное задание в окно связи,         │
│               дальше борт решает сам                          │
└───────────────────────────┬──────────────────────────────────┘
                            │  только dict действий
                            ▼
┌──────────────────────────────────────────────────────────────┐
│  МОДЕЛЬ ГРУППИРОВКИ (выдана организаторами) — НЕ ИЗМЕНЕНА     │
│  model/resource_env.py · model/operations.py                  │
│  энергия · температура · допуск действий · учёт выполнения    │
└──────────────────────────────────────────────────────────────┘
```

**Три факта в подвал слайда:**

- Весь backend — **три зависимости**: FastAPI, uvicorn, pydantic. Ни numpy, ни scipy, ни ML-библиотек. Венгерский алгоритм написан руками и сверен со `scipy` на 300 матрицах.
- Сама модель кейса не тянет **ничего**: только стандартная библиотека Python 3.10+.
- Граница одна: планировщик отдаёт словарь действий, всё остальное считает `env.step`. Поэтому `replay_episode` сходится, а учёт остаётся эталонным.

## Слайд Б. «Как мы добились эффекта»

**Подзаголовок:** Пять инженерных решений, каждое — ответ на конкретное измеренное препятствие.

| Препятствие | Что сделали | Эффект |
|---|---|---|
| `observation()` копирует все 8 120 заданий на каждом шаге | Инкрементальный индекс `ScenarioIndex`: окно активных заданий обновляется на выпуске, дедлайне и завершении | Полная смена на `P04_demand` — **5.5 с** при бюджете 20 |
| Теневые цены пересчитывались с нуля и прыгали, аппарат бросал начатое ради соседа | Планировщик живёт **между** шагами: экспоненциальное сглаживание цен, гистерезис вытеснения | Нестабильность **26.7% → 21.8%**, выручка при этом растёт |
| Борта не могут договориться на лету, а downlink-слотов два на всю группировку | Земля раскладывает конкретные шаги по бортам **заранее**, внутри полётного задания | Конфликтов `ground_capacity` в журнале **ноль** — закреплено тестом |
| Журнал решений — 26 МБ на прогон, а панель разбора обязана открываться за 300 мс | Два уровня: кандидаты и цены хранятся всегда, глубокая часть восстанавливается по запросу и кэшируется | Панель **8–30 мс** на любом шаге вместо 5.1 с |
| Полное полётное задание в каждом сеансе — лишний трафик | Земля помнит, что лежит на борту, и шлёт только разницу; сравнивает дельту с полным и шлёт меньшее | Трафик **7.1 → 1.5 МиБ** за смену, ухудшить объём кэш не может |

**Нижняя плашка:**

> Каждое решение сначала измерено, потом внедрено. Отвергнутые варианты сохранены с числами: венгерское назначение (выигрыша нет), безусловное «добивать начатое» (−$11 977), вычитание всех теневых цен внутри приоритетного разряда (−4 задания P3).

## Слайд Г. «Зачем нужен централизованный режим»

Формулировка «требует связи на каждом шаге — чего в реальности нет» звучит как
оправдание и обесценивает наш же основной режим. Она неточна.

**Централизованный режим — это ровно то, что моделирует кейс.** Проверяется одной
командой: на шаге 20 сценария `P01_intro` у всех аппаратов недоступны оба канала,
но команда `calibrate` доходит и исполняется.

```
шаг 20 | связь у группировки: нет
команда calibrate без связи -> исполнено: calibrate | причина: accepted
```

`env.step(actions)` принимает команды для всех аппаратов независимо от связи.
Ограничения `downlink_available` и `relay_available` действуют на **выполнение
оплачиваемых заданий**, а не на доставку команд. Командного канала в модели нет
вовсе.

**Отсюда правильная расстановка:**

| Режим | Что это на самом деле |
|---|---|
| `centralized` | **режим кейса** — допущения выданной модели без изменений. На нём нас и оценивают по правилам задачи |
| `federated` | **режим реальности** — наше расширение: мы САМИ добавили ограничение, которого в модели нет |

Четыре причины, по которым централизованный режим остаётся основным:

1. **По правилам задачи он корректен.** Жюри загрузит свой сценарий, подаст
   сообщения и будет оценивать результат по модели организаторов. Отказаться от
   режима, который эта модель задаёт, значит добровольно ухудшить свои числа.
2. **Без него нельзя измерить автономию.** Фраза «сеанс раз в четыре часа стоит
   5% выручки» имеет смысл только относительно точки отсчёта.
3. **Это эталон корректности.** Простейшая топология, на которой проверяются
   разрешение конфликтов, защита шлюза и правила сроков.
4. **Он честно назван.** Не «верхняя граница» — это эвристика, а не оптимум.
   База сравнения.

**Формулировка для слайда 7 вместо нынешней:**

> `centralized` — допущения кейса как есть: модель доставляет команды всегда.
> `federated` — ограничение, которое мы добавили сами, потому что в реальности
> связь есть только в окнах контакта. Разница показателей и есть цена автономии.

Это сильнее: мы не оправдываемся за нереалистичный режим, а показываем, что
**сами нашли и измерили ограничение, которого организаторы не заложили.** Ровно
то, за что даются баллы по критерию О7.
